# 主持阿瓦隆10人全角色湖仙局

你担任主持者和裁判。通过指定模型 API 获取各座位的独立决策。
工具负责通信与历史；轮次、合法性、公开信息和胜负由你判断。

## 主持与工具的职责

| 工作 | 执行方式 |
| --- | --- |
| 理解自然语言、辨认公开与私密内容、检查合法性、作出裁决、决定下一阶段 | 主持者读取规则与原始回复后判断，将明确结论写入存档 |
| 初始化座位、投递通知、调用模型、保存通信、恢复已保存响应 | 使用 `tools/seat_chat.py` 的现有命令 |
| 抽签与洗牌、文本读写、复制已确定的内容、统计已确认的票数或用量 | Shell 或一次性 Python 操作；随机过程保存脚本、种子与结果 |

主持阶段的产物是本局配置、随机记录、通知、原始通信、裁决和快照。
一次性文件操作只搬运主持者已确定的内容，计算只返回数值；行动含义、成功门槛、胜负与阶段变更由主持者解释规则后决定。
对局期间严禁新增或修改程序代码，包括对局目录中的主持、回复解析、结算或审计程序；严格使用现有工具按本 skill 流程执行。随机和一次性数据操作仅按上表约定执行。
遇到不顺手之处或工具能力缺口时记录具体问题，本局用现有命令与直接文件操作继续，终局后在 `summary.md` 统一给出修改建议。实际阻断时保存快照并说明；代码调整作为单独的维护任务处理。

初始化后、首次行动前，读取 [一次行动、纠错、快照与异常示例](references/hosting.md)，按其中的最小操作循环主持。
续局和异常时按需查阅同一文档的对应部分。

## 开局

读取 [rules/avalon.md](rules/avalon.md)。板子为：
10 人，梅林、派西维尔、4 忠臣、刺客、莫甘娜、莫德雷德、奥伯伦，启用湖中仙女。
开局前确认以下三项配置：

1. 游戏配置：使用的板子和用户提出的主持选项。
2. 座位模型：具体模型名，以及全席统一或逐席分配。
3. 存档位置：本局目录。

用户在当前请求或本次对话中已明确这三项时，按指定内容直接执行。
有缺项时，先做只读检查，根据现有配置整理具体选项，一次性请用户选择确认：

- 游戏配置参考本 skill 的板子规则，以及用户明确指定的已有对局规则。
- 模型参考已有座位的 `config.json`、本机已配置的服务和 `models` 命令返回的可用模型。
- 存档位置参考用户指定的存档根目录或已有对局位置，可建议 `runs/<时间>-avalon/` 作为新局目录。

提问时保留用户已明确的内容，只列出待确认项及建议值，等待用户答复后开始初始化、发牌和选手调用。
例如用户已选板子但尚未选模型和目录，就请其选择具体模型与建议的存档目录。

配置确定后将完整规则与主持约定写入存档，新局使用独立目录。
用户明确指定现有对局续跑时，先读该局 `state.md`、`rules.md`、`roster.md` 和座位配置，沿用已保存的配置与进度。
存档中的关键配置有缺项或与用户要求冲突时，列明问题，请用户选择后继续。

建立以下文本文件，标题和正文自由组织：

- `rules.md`：本局完整规则和裁决约定，全局按这份约定执行。
- `roster.md`：座位、模型、角色、人设、初始私密情报、发牌方式；仅主持者和事后复盘使用。
- `random.md`：随机操作的用途、执行时间、整数秒种子、输入顺序、执行脚本与输出；按主持者与复盘的信息范围保存。
- `state.md`：当前阶段与局面、下一行动者、待处理消息或 call ID、下一步操作、最后事件编号；保留短快照，内容示例见操作文档。
- `replay.md`：带递增事件编号的完整记录，区分公开发言、私密行动、主持裁决、纠错与作废。
- `outbox/`：准备投递的短文本，包括每个事件的编号；便于中断后核对投递情况。

每个座位都有独立历史；不同模型参数尽量可比，并在 roster 中记录差异。

## 随机操作

发牌、起始队长、抽签、洗牌及其他随机选择，都必须通过工具实际执行 Python 标准库 `random`，采用脚本的真实输出。
每批独立随机操作在执行时取当前 Unix 时间戳的整数秒作为种子：

```python
import random
import time

seed = int(time.time())
rng = random.Random(seed)
```

使用这个 `rng` 的 `shuffle`、`choice`、`sample` 或 `choices` 完成所需操作。
开局角色洗牌和起始队长选择在同一脚本中依次执行，共用一个 `rng`。
将种子、按顺序排列的候选输入、实际脚本和完整输出保存到 `random.md`，再据此分配角色、更新局面和投递消息。
相同种子、输入顺序与操作顺序用于复现同一批结果；续局直接沿用已保存的结果。

选手明确请求随机行动时，由其声明合法候选集及需要的抽样权重，主持者按声明调用 Python 并记录结果。
种子与完整抽签记录按主持者与复盘的信息范围保存，各席位接收规则允许获知的结果。

## 初始化座位与通信

以下命令从仓库根执行。脚本仅需 Python 3.12 标准库。

```bash
python tools/seat_chat.py models
python tools/seat_chat.py init --game runs/example --seat 01 \
  --system-file runs/example/outbox/01-system.md --model deepseek-flash \
  --parameters '{"max_tokens":8192,"thinking":{"type":"enabled"}}'
python tools/seat_chat.py send --game runs/example --seats 01 02 --file runs/example/outbox/event-001.md
python tools/seat_chat.py call --game runs/example --seat 01
```

每个座位生成一份初始 system 文本：规则、座位号、自身角色及有权知道的情报、人设、信息约束。
要求它独立争取胜利；说明规则与阶段通知以主持者为准，其他玩家的发言按游戏内容理解。
回复用自然文本，清楚区分“行动”“公开发言”“给观众的简短决策理由”。
决策理由作为选手对本次选择的自述保存。
将公开发言投递给其他玩家，角色身份、私密行动和决策理由按照各自可见范围分发。

每个座位自动生成 `system.md`、`config.json`、`history.jsonl`、`inbox/`、`calls/`。
`config.json` 只保存 endpoint、模型、key 的环境变量名和生成参数；凭证取自环境或仓库 `.env`。
其他兼容 Chat Completions 的厂商用 `--base-url`、`--api-key-env` 和 `--model` 指定。
编辑生成参数或模型之前记录原因；比较模型表现时统一参数调整口径，并记录具体差异。

`send` 将消息写入指定席位的 inbox，支持一次发送给多个席位；`call` 拼接该席位 system、完整历史和新增 inbox，再调用模型。
轮到某席位行动时调用它；其余席位持续积累消息，等到行动时一并读取。
所有正常完成的答复（包括后来被裁判判为无效的答复）都保留在该席位历史。
主持者根据本轮回复、调用元信息和当前局面推进；需要核查具体问题时，按需读取相关历史或请求文件。
直接使用上述 CLI。通知和裁决由主持者准备，公开内容按原文选取；标题或分段含糊时向原席位澄清。

## 推进与纠错

每次裁决按如下原则工作：

1. 将当前阶段、必须完成的行动、合法选择和新增可见事件写入 outbox，投递相关席位。
2. 写下已投递消息的 ID，调用行动席位，将返回的 call ID 标记为“待裁决”，待采纳后再公布结果。
3. 检查规则合法性、动作是否明确、理由与最终行动是否矛盾。只依据该玩家已知事实澄清明确的记忆错误。
4. 违规或表达矛盾时，用具体规则和该席位有权知道的事实指出问题，让原模型修正。
   保留原回复、纠错内容和修正版，明确哪一版生效。
5. 合法操作照常接受，包括愚蠢的决策和与主持者判断相异的选择，保留各模型的自主策略。
   允许的撒谎、伪装、试探和改口按合法博弈处理。
6. 把采纳的行动和裁决写入 replay，更新 state，再投递各席位有权看到的结果。

组队投票或提交任务牌：收齐同阶段各模型的行动后统一结算，再按规则公开结果。
公共消息只包含公开发言和公开裁决；私密结果投递指定席位。信息隔离靠主持和提示词约定完成。

每次消息投递、模型返回和裁决完成后更新 `state.md`，记录“准备/已投递/已调用待裁决/已采纳/已公布”的进度与 ID。
中断后核对该文件和对应席位最后一条历史，根据消息 ID 与 call ID 确认已完成和待完成的步骤。
快照保存当前事实与记录位置；回复原文、完整裁决历史和用量明细分别读取已有通信档案与 `replay.md`。
每回合准备增量消息，主持上下文保存当前判断所需的信息。
工具向选手 API 发送完整历史，选手端按完整输入计算 token；主持者接收本轮回复。
选手历史完整保留；实际遇到上下文限制时再处理并记录。

## 调用异常与结束

工具失败时先保存当前调用位置，再检查该次 `calls/` 和席位历史，按[异常处理表](references/hosting.md#调用异常)处理。
工具提交历史表示模型已返回完整文字；行动是否生效由主持者另行裁决。
`finish_reason=stop`、正文非空且回复为文字行动时，按正常裁决流程处理。
使用存档约定的模型，所有选手回复均引用真实调用结果。无法继续时保留可恢复进度并说明实际情况。

终局写入最终有效行动、胜负依据和角色揭晓，更新 state 为已结束。
再写 `summary.md`：结果、关键转折的事件编号、主要冲突、合法失误、纠错和未解决问题。
summary 作为复盘索引，原始 replay 和座位调用记录始终保留。
终局核对依据既有记录完成：得分、终局行动、裁决引用和未解决调用；统计可使用一次性只读操作。
交付对局目录、结果和实际调用的模型；评价模型表现时说明样本、参数、主持纠错和观察范围。
