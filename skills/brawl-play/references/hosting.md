# 主持操作示例

以下示例使用仓库根目录和 `runs/example`，具体席位、文件名、事件编号和 call ID 均按当前存档填写。
示例用于说明操作顺序，所有实际选手发言与行动以 API 原始回复为准。
文件创建、追加和快照替换可以使用现有文件编辑工具、Shell 或一次性 Python。

## 一次公开发言

前提：十席已用 `init` 初始化；第一任务队长03提出队伍03、05、08，目前轮到04发言。

1. 主持者写 `outbox/E0010.md`，例如：

   ```text
   E0010｜任务1，逐席发言，轮到04。
   当前提案队伍：03、05、08；任务人数3；比分0:0；连续否决0。
   请发表本轮公开意见，并给出观众可见的简短理由。
   ```

2. 在 `state.md` 标记“准备投递E0010，下一操作send”。执行：

   ```bash
   python tools/seat_chat.py send --game runs/example --seats 04 --file runs/example/outbox/E0010.md
   ```

   把命令返回的 message ID 写入快照，标记“已投递，下一操作call”。

3. 调用该席位：

   ```bash
   python tools/seat_chat.py call --game runs/example --seat 04
   ```

   保存返回的 call ID 与档案路径，在快照标记“已调用待裁决”。
   主持者直接读取返回的完整文字，辨认行动、公开发言和观众理由，依据规则判断。

4. 行动合法时，在 `replay.md` 追加裁决事件E0011，注明对应 call ID、采纳结果和裁决依据。
   原始答复已在席位历史中，记录可以用路径和 call ID 引用；有必要展示的部分按原文保留。
   这次是发言阶段，公开的赞成或反对倾向按发言记录，正式票在投票阶段另行收取。
   更新快照为“已采纳，公开发言待投递”。

5. 主持者将原回复中的公开发言单独写入 `outbox/E0012.md`，注明事件编号与04号说话人，并关联裁决E0011。
   观众理由留在主持记录中。投递给十席：

   ```bash
   python tools/seat_chat.py send --game runs/example --seats 01 02 03 04 05 06 07 08 09 10 --file runs/example/outbox/E0012.md
   ```

   将 message ID 与接收席位追加到对应事件，更新快照为“04已公布，下一行动者05”。
   给05准备的通知只包含新增局面和当前行动要求，既有发言由工具随其历史与 inbox 一并发送。

## 违规后的追问

例如原席位在发言中明确把“好人可以交失败牌”当作游戏规则：

1. 在 `replay.md` 引用该 call ID，标记“作废，待同席修正”，写明具体规则冲突。
2. 主持者写一份定向纠错文本，例如：

   ```text
   E0013｜本轮发言待修正。
   规则规定好人只能交成功牌，坏人可交成功或失败。
   请修正规则表述，完整重答当前发言；保留你自己的怀疑、立场和策略选择。
   ```

3. 用 `send --seats 04 --file <纠错文件>` 投递，再用 `call --seat 04` 获取原模型的修正版。
4. 在记录中关联原 call ID 和修正 call ID，依正常流程决定采纳并公布哪一版。
   两次完整回复都留在该席位历史，生效版本由裁决指出。

角色允许的谎言和策略判断按合法博弈处理。公开与私密内容分段不清、动作含糊时，定向请原席位澄清。

## 秘密投票与任务牌

- 同阶段对每名有行动资格的席位投递要求，各自调用并标记待裁决。组队票由十席提交，任务牌由本次队员提交。
- 收集期间保存回复和 call ID，收齐后由主持者确认每个动作的含义与合法性。
- 可用一次性 Python 对主持者已确认的票值计数；主持者按 `rules.md` 判断通过、任务结果、得分和下一阶段。
- 公开组队票的各席位票型；任务牌公开总数。主持者准备公开结果文本，投递后更新快照。
- 公开发言按顺序逐席处理，后一席读取此前已公布内容；秘密行动收齐后统一结算。

## 当前状态快照

`state.md` 可按以下形式自由组织，字段按实际阶段取舍：

```text
# 当前对局
阶段：任务1逐席发言
队长：03；队伍：03、05、08
比分：好人成功0，任务失败0；连续否决0
湖仙持有人：02；历史持有人：02
进度：04发言已采纳，公开内容待投递
当前行动引用：04 / <真实call-id>；裁决见 replay.md 的 E0011
待处理投递：outbox/E0012.md，接收01至10，尚待send
下一步：投递04公开发言，记录message ID，再准备05通知
最后完成事件：E0011
```

快照保存当前事实、待办和必要索引，私密结果按需引用其存档位置。
完整回复和调用用量查席位档案，完整事件与裁决查 `replay.md`；每个回合更新当前快照即可。
新建的记录和通知各使用独立事件编号，通过 call ID 和事件引用关联，消息发送后记录实际 message ID。

## 续局与操作中断

读取快照后，按待办核对原始记录，再继续尚未完成的步骤：

| 快照或现场状态 | 核对与操作 |
| --- | --- |
| 通知已准备，发送状态待核对 | 查目标席位 `inbox/` 中的事件编号与通知正文；已存在时补记 message ID，否则执行send |
| 通知已投递，调用状态待核对 | 查该席位最新调用目录与 `input.json`、历史中的 inbox ID，确定这条通知是否已有返回 |
| 席位历史已新增完整回复，裁决待完成 | 读取这次回复，由主持者完成裁决 |
| 裁决已采纳，公开内容待投递 | 核对接收席位 inbox，完成缺少的公开投递并更新快照 |
| 调用已经发出，暂时没有可确认的完整响应 | 核对活动进程与调用目录，记录调用状态，按下表处理 |

记录步骤处于“待核对”时先核查证据，依据实际完成情况推进。
直接读写文本与调用现有CLI即可完成这些操作；对局进度由主持者依据快照和记录判断。

## 调用异常

先查看该次 `calls/<call-id>/` 下的 `status.json`、`response.json`（若有）及席位历史。

| 情况 | 处理 |
| --- | --- |
| 已保存完整文字响应，历史尚未提交 | 使用 `call --recover <call-id>` 提交已保存响应，再由主持者裁决 |
| 历史已有这次call ID | 从这条回复继续完成待办 |
| 正文为空、`finish_reason=length` 或返回工具调用 | 保留原始记录，标记这次尝试无有效文字行动；核查后可按同模型、同参数再次call |
| 网络中断、没有完整响应 | 保留输入与尝试，注明远端是否完成及用量未知；先核查活动进程和本地记录，确认本地没有待收取结果后决定再次call |
| 认证、额度、参数或服务配置错误 | 记录错误与当前进度，修复对应问题后继续；涉及模型或生成参数调整时记录原因和具体差异 |

恢复命令：

```bash
python tools/seat_chat.py call --game runs/example --seat 04 --recover <真实call-id>
```

空正文和截断时，依据实际 `finish_reason` 与正文记录问题，行动以完整文字为准。
新尝试成功后，在 `replay.md` 关联原尝试与新call ID；远端结果仍未知的部分继续如实保留。

## 终局核对

主持者根据 `rules.md` 和既有记录核对任务成绩、最终行动及胜负依据，确认每个待处理调用的结论。
一次性只读操作可以统计调用次数、用量和列出异常记录；核对结论写入 `summary.md`。
将对局中记录的不顺手之处和工具能力缺口汇总到 `summary.md`，给出修改建议，作为终局后的独立维护事项。
