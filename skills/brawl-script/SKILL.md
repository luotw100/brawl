# 从阿瓦隆对局生成剪辑脚本

对局是已经发生的素材。你担任编导和剪辑师，从生效记录中选择、组织和呈现故事；游戏行动与胜负以原存档为准。

## 已确认的默认偏好

| 项目 | 默认值 |
| --- | --- |
| 形式 | 玩家原话为主的精剪对局，少量旁白连接、解释 |
| 观众视角 | 跟随公开信息推理，在关键节点逐步揭晓身份和私密行动 |
| 目标观众 | 懂阿瓦隆基础规则，特殊规则和复杂推理按需解释 |
| 成片预算 | 16:9 横屏，约 10–15 分钟 |
| 语言 | 简体中文；玩家原话保留原语言与措辞 |

用户当次要求优先于默认值，已确定的选择不再反复询问。风格以实际素材为依据，不强迫每局都有逆转、主角或惊天反转。

## 输入、边界与输出

先确认目标对局。已指定目录就使用该目录；未指定时查看 `runs/` 的状态，若只有一局明确已结束可直接选用并说明；有多局且无法判断目标时，一次问清。未结束的对局只能按用户要求制作阶段片段，不替它预写结局。

按职责读取素材：

- `state.md`：是否终局、最后事件和待处理事项。
- 本局 `rules.md`：本局实际规则；缺失时参考 `../brawl-play/rules/avalon.md` 并注明待核实的差异。
- `summary.md`：发现转折和检索线索，不当作唯一事实依据。
- `replay.md`：完整事件、公开/私密范围、采纳、作废与修正。
- `public.md`、`roster.md`：若存在，分别辅助核对公开正文与角色。公开文件也可能含终局揭晓，不能整份直接用于开场。
- 座位历史及 `calls/`：有具体疑点时才读取对应调用；仅使用正文，不将隐藏思考或调用元数据写成玩家台词。
- `host-state.json` 等辅助文件：若存在，只作索引或交叉核对；不是每局必须具有的接口。

不要调用玩家、续跑比赛或改写主持存档。默认在本局的 `video-script/` 新建本工作流文件，用户指定输出位置时使用其位置。保留用户已有版本，续改时先读已有脚本与审稿记录。

最终交付四份 UTF-8 Markdown，详细格式见 [脚本格式与选材示例](references/script-format.md)：

| 文件 | 职责 |
| --- | --- |
| `brief.md` | 当集目标、风格覆盖项、素材范围、叙事主线、观众信息揭示计划 |
| `selects.md` | 候选素材、原事件定位、有效版本、保留/压缩/舍弃的理由及必要前提 |
| `script.md` | 可供配音与画面制作使用的逐段视听脚本、预计时长、来源引用 |
| `review.md` | 事实、叙事、信息范围和节奏检查，实际修订及尚未解决的问题 |

这里只生成脚本和制作指令。时间是估算；音频、表情、配乐、图片等尚未制作的素材应明确标为制作需求。

## 工作流

### 1. 读完整局，建立生效素材索引

先通读完整对局，再决定取舍。记录输入路径、已读范围和最后事件，实际计算所用源文件的 SHA-256，写入 `brief.md`；续改先核对来源是否变化。

区分玩家原答、公开广播、裁决与修正版。同一发言只选一份有效正文；作废原答、空回复和未采纳行动不进入正常剧情。若纠错本身值得讲，明确标注为纠错插段，保留真实处理顺序，不伪装成已广播发言。

为候选素材记录来源、游戏阶段、说话人、有效性和原始信息范围。每段引用用“源文件路径 + 事件编号 + 原文摘录”定位；必要时附 call ID。没有事件号时使用该存档现有的稳定定位，不臆造事件编号。

### 2. 找到本局值得观看的问题

在素材中找冲突、判断分歧、欺骗、规则约束、结果反差和可回收的早期线索。评估候选段是否改变局面、提出问题、提供证据或完成回应；单纯情绪强烈不足以入选。

按素材考虑一到三个可成立的主线，记录选择理由并自行选定最合适的一条；用户要求先选方向时才停在这个节点。选定中心问题、主要对立、关键转折与收束，说明哪些支线压缩。

例如，任务逆转与刺杀可以构成一条故事；也可能整局最值得讲的是一次错误查验声明。不要提前把每个玩家分配到英雄或反派模板，也不要求十席时长平均。

### 3. 安排观众获得信息的顺序

编导可以知道全部身份，观众在默认视角下仍从有限信息开始。为会影响理解的秘密记录：来源事件、游戏中何时发生、何时在成片揭示、揭示前使用什么说法、为什么此时揭示。

正文以游戏时间顺序推进。提前展示后段片段时标记“稍后”，回放标记原任务或阶段；不能让后发生的发言看起来曾影响此前投票。开场可以提出悬念，不默认透露刺杀目标和最终胜负。

检查所有信息出口：旁白、字幕、标题、身份色、头像、任务牌归属、湖仙真实结果和观众理由。玩家声称“我是好人”只是声明；图形不能替它做身份认证。推理可以讲清，但不要把玩家尚不知道的结论塞进其发言。

### 4. 先搭段落，再写声音与画面

每段写明：叙事任务、进入时观众知道什么、使用哪些事件、结束时新增什么信息、预计时长。对重复的表态选最有辨识度且保留必要前提的部分，其余可用中性字幕或旁白概述。

优先让关键玩家原话推动剧情。新增旁白负责补足上下文、连接被压缩的阶段和解释难懂的票型，不代替所有争论。读不完的全屏长文改为分句、证据卡或精确选段。

画面指令描述观众实际需要看见的内容：当前队伍、发言双方、前后票型或失败牌总数。需要观众比较时给阅读时间；不按固定秒数强行切镜头。没有记录的惊讶、犹豫或生气不能写成真实反应镜头。

### 5. 写成可制作、可追溯的视听脚本

按格式参考为每个声音块和画面动作分配稳定 ID。明确区分玩家原话、旁白、主持公告、玩家自述的观众理由、字幕和制作指令。

玩家原话可选取完整句段，不能为了顺口重写或拼出新含义。不连续摘录分成不同声音块，省略记在来源说明中；缩写后的意思改由旁白或字幕表达。姓名、座位号等需要口播展开时保留引用原文，另列朗读处理。

旁白的事实与推论都指向证据；将“规则可推出”“玩家这样认为”“玩家自述”“编导推测”分清。观众理由只代表玩家当次自述，不声称读出了真实内心。

### 6. 估时、审稿并修订

先以每分钟约 240 个中文口播字作为工作估值，可按试读和内容密度调整；这是预算假设，不是实际语音速度。计算实际口播内容，并加上独占的翻牌、读图和停顿时间。与口播并行的画面时间不能再重复累加。

超预算先删弱支线、重复表态和重复解释，再修整旁白。保留论据、限定语和结果所需的时间，不能仅靠提高语速塞入目标长度。素材不足时如实给出更短方案；内容确需更长时交代取舍与估算，不能虚报达标。

按 [审稿标准](references/editorial-review.md) 复读来源和成稿，先修事实与剧透，再修结构、理解门槛、节奏和文字。把关键改动及原因写进 `review.md`，完成修订后交付。

用户只要求工作流时，不自动替某局生成全片脚本。用户要求生成脚本时，完成上述流程，不额外设置默认的逐阶段确认门槛；只在缺少关键事实、目标不明或用户指定检查点时停下。

## 交付与续改

交付四个文件路径、主线、预计时长和实际验证范围。未经配音和成片观看，只能称“文字审稿完成、待配音校时”，不能宣称已经好看、音画同步或时长验证通过。

收到修改意见时，按段落/声音块 ID 或台词定位；保留仍生效的素材引用，更新受影响的时长、揭示计划和审稿结论。单集改动写入本集文件；长期偏好只有用户明确要求时才修改本 skill 的默认值。

工作流参考的开源项目及采用范围见 [来源说明](references/sources.md)，无需安装它们即可执行本 skill。
